## はじめに — この資料の性格について

**ここに書かれている見た目は、実機の計測値ではありません。**

作った人間の**実機の記憶**を出発点に、**公開されている仕様書・技術資料・ウェブ上の画像**を突き合わせて組み立てたものです。分光器で測ったわけでも、オシロで応答を取ったわけでもありません。

したがって、

- **数値には「実機がそうだった」という保証はありません。**「この値だとそれらしく見える」という調整の結果です
- **出典のある部分と、そうでない部分が混在しています。**色補正の行列や境界値のように他の実装・文献から取ったものは出典を明記し、質感まわりのように調整で決めたものは「調整値」と書きました

**再実装する方へ。** この資料の目的は「brickboy と同じ絵を出す」ことであって、「実機を正しく再現する」ことではありません。この 2 つは重なる部分が大きいはずですが、同じではありません。より確かな計測をお持ちなら、そちらを優先してください。

## 1. 全体の構造

エミュレータのコアが吐くのは **160×144 の生のフレームバッファ**だけです。DMG なら 1 画素 2bit の階調（0〜3）、CGB/GBA なら BGR555。ここから先が表示の作り込みで、**6 つのパスを決まった順に通します。**

```
        コア（160×144, R16UI）
              │
    ┌─────────┴─────────┐
    │ PRE-PASS 列の暗さ  │  160×1 に潰す。クロストークの材料
    └─────────┬─────────┘
              ▼
    ┌───────────────────┐
    │ PASS 1 色補正      │  階調→sRGB、濃度、クロストーク、
    │                   │  彩度・ガンマ・明るさ・黒浮き
    └─────────┬─────────┘
              ▼
    ┌───────────────────┐
    │ PASS 2 ドット構造   │  格子・リフレクタ・落ち影・紙の粒
    └─────────┬─────────┘
              ▼
    ┌───────────────────┐
    │ PASS 3 残像        │  1 画素ごとのアナログ状態を保持
    └─────────┬─────────┘
              ▼
    ┌───────────────────┐
    │ PASS 4 故障        │  劣化。すべて既定 0（＝素通し）
    └─────────┬─────────┘
              ▼
    ┌───────────────────┐
    │ PRESENT 仕上げ     │  面内むら・粒・周辺減光
    └─────────┬─────────┘
              ▼
           画面（キャンバス）
```

### 順序が変えられない理由

**残像（PASS 3）はドット構造（PASS 2）の後**です。実機で残るのは「液晶の状態」であって「格子の隙間」ではありませんが、格子を後から掛けると残像の尾にまで格子が二重に乗ります。ドット構造まで作った絵を状態として保持するほうが、結果が実物に近くなります。

**故障（PASS 4）は残像の後**です。ライン抜けは液晶が動かない箇所なので、**残像しません**。先に故障を乗せると、抜けた線が尾を引きます。

**クロストークは PASS 1** です。これは電気的な現象（列電極を共有する画素が干渉する）で、光学的な劣化とは別物なので、色を決める段階で入れます。

### 実装上の重要な制約

- **中間バッファは浮動小数点**にしてください。8bit だと残像の指数減衰が量子化で階段になります
- **バックバッファは「実際の画素数ちょうど」**に取ってください。整数倍でない拡大をブラウザ／OS に任せると、合成したドット格子が再標本化されて**モアレになります**
- **残像には 2 枚のバッファを ping-pong** させます（読みながら書けないため）

## 2. PRE-PASS — 列ごとの暗さ集計

**目的**: パッシブマトリクス液晶のクロストークを出すための材料を作る。

160×144 を **160×1** に潰し、列ごとの「暗さの平均」を出します。

```glsl
// DMG: 階調 0..3 → 0..1 の暗さ
darkness = min(native, 3) / 3.0

// CGB/GBA: BGR555 の合計から暗さを出す
darkness = 1.0 - (r + g + b) / 93.0     // 31*3 = 93
```

この列プロファイルに 2 つの味付けをします。

**列ごとの利得ゆらぎ**（`crosstalkNoise`）: ドライバ IC の個体差。`hash21(col, seed)` で列ごとに固定のゆらぎを与えます。**時間では変化しません**（毎フレーム振ると画面が沸きます）。

**エッジ検出による帯**（`crosstalkEdge`）: 明暗の境目で干渉が強く出る性質。隣の列との差を取って重み付けします。

> **なぜ 1 次元に潰すのか**: 実機のクロストークは「同じ列の他の画素が暗いと、その列全体が影響を受ける」現象です。2 次元のままフィルタを掛けると、単なるぼかしになって現象が違ってしまいます。

**この処理は、クロストークが 0 のときは丸ごと省略します。**

## 3. PASS 1 — 色補正と液晶の電気的な癖

### 3-1. 階調 → sRGB

3 つのモードがあります。

| モード | 対象 | 変換 |
|---|---|---|
| `dmg-lut` | DMG / Pocket / Light | 階調 0〜3 を **4 色のパレット**へ引く |
| `cgb-byuu` | GBC | BGR555 → sRGB。**byuu/ares の整数行列** |
| `gba-byuu` | GBA 系 | byuu の GBA ガンマ（lcdGamma 4.0 / out 2.2 / ×255÷280） |

CGB と GBA の変換は **ares の実装（`gb/ppu/color.cpp`, `gba/ppu/color.cpp`）** をそのまま使っています。ここは調整値ではなく、既存の実装に合わせた部分です。

DMG のパレットは SameBoy の `GB_PALETTE_DMG` を出発点に調整したものです。**現在の値は出発点からずれています**（§10-④参照）。

### 3-2. 処理の順序

**この順序を変えると絵が変わります。** 上から順に適用します。

```
 1. 階調 → sRGB（上記）
 2. STN にじみ（bleed）        隣接画素と 0.25 の重みで混ぜる
 3. 濃度ダイヤル（density）     0.5 が中立
 4. 消灯画素の色被り（offTint）
 5. クロストーク（crosstalk）
 6. パネルガンマ（panelGamma）  pow(rgb, γ)
 7. 彩度（saturation）          輝度との mix
 8. 暖色寄せ（warm）
 9. コントラスト（contrast）    (rgb - 0.5) * c + 0.5
10. 明るさ（brightness）        rgb *= b
11. 黒浮き（blackLift）         紙の色へ mix
```

### 3-3. 濃度ダイヤル（実機側面のつまみ）

```glsl
if (density > 0.5) rgb = mix(rgb, palette[3], (density - 0.5) * 2.0);
else               rgb = mix(rgb, panelBg,    (0.5 - density) * 2.0);
```

**階調3 を不動点として、他をそこへ寄せる式**です。したがって、

- 階調3 は自分自身と混ざるので**変化しない**
- 階調0 は最も遠いので**最も大きく動く**

実測（濃度 0.50 → 0.90 の輝度変化）:

| 階調 | 0.50 | 0.90 | 変化 |
|---|---|---|---|
| **0（最明）** | 0.4145 | 0.1663 | **−60%** |
| 1 | 0.3156 | 0.1655 | −48% |
| 2 | 0.1709 | 0.1318 | −23% |
| **3（最暗）** | 0.1123 | 0.1008 | **−10%** |

実機で遊んでいた人の「濃くすると階調3 はあまり変わらず、階調0 がいちばん変わる」という証言と、順序まで一致しました。

**濃度は色も動かします。**上げるほど画面全体が階調3（濃い緑）へ寄るため、**暗く、かつ緑が強くなります**。

| 濃度 | 0.30 | 0.50 | 0.70 | 0.90 |
|---|---|---|---|---|
| 画面全体の G/R | 0.93 | 1.00 | 1.12 | 1.18 |

> **重要**: **「正しい濃度」は存在しません。**適正値は視環境で変わります（§9-2）。実機に物理つまみが付いていたのはそのためで、固定値で足りるなら付ける必要がありません。brickboy の既定は 0.5 ですが、これは「中立」という意味であって「正解」ではありません。

### 3-4. クロストーク

4 つの成分に分かれています。

| パラメータ | 何をするか |
|---|---|
| `crosstalk` | 主強度。列の暗さに応じて、その列全体を沈める |
| `crosstalkSigned` | 明るくする方向にも効かせる（実機は両方向） |
| `crosstalkGrayField` | 中間調で最も目立つ性質（`grayField` で重み付け） |
| `crosstalkEdge` | 明暗の境目で強く出る |
| `crosstalkNoise` | 列ごとの固定ゆらぎ（ドライバの個体差） |

**温度で強まります**（`temperature`）。冷えたパネルはクロストークが増えるという性質を、`tempMul` として掛けています。

![生のフレームバッファ](images/display/01-native-tone.png)

**パイプラインを通した後:**

![描画後](images/display/03-rendered-tone.jpg)

### 4-2. ドット構造の拡大

![ドット構造の拡大](images/display/04-dot-structure.png)

*診断 ROM の格子ページ。4 倍に拡大（補間なし）。*

読み取れる要素:

- **ドットは正方形に近く、四辺に隙間**がある（`pixelSize` が占有率）
- **隙間にはリフレクタの色**が見える（`bgTint`）。暗い格子線ではない
- **各ドットは右下方向へ落ち影**を落とす（`shadowOffset` / `shadowBlur` / `shadowOpacity`）
- **紙のような粒**が全面に乗る（`paper` / `paperScale`）
- **明るい階調では格子が弱く、暗い階調で強い**

### 4-3. 隙間の色

```glsl
vec3 gap = bgTint * (1.0 - shadowOpacity * 0.4);
vec3 gridded = mix(gap, mix(bgTint, lit, 1.0 - baselineAlpha), body);
```

**隙間は「暗い線」ではなく「リフレクタが見えている場所」**です。ここを暗くすると、明るい面にまで黒い格子が乗って別物になります。

実測した格子の変調量（明るい一様面での山谷／平均）:

| | 実機写真 | brickboy 階調0 | brickboy 階調1 | brickboy 階調3 |
|---|---|---|---|---|
| 格子の見え方 | 1.2% | **3.7%** | 17.3% | **31.4%** |

**明るいほど格子が薄く、暗いほど濃い**という方向は、物理的に正しい向きです（明状態では画素も隙間も同じ反射面だから）。

### 4-4. 落ち影

液晶層とリフレクタの間に**空気層**があるため、暗いドットは背後の反射面に影を落とします。

- `shadowOffset` 1.35（ネイティブ画素相当）— 光源の方向へずらす量
- `shadowBlur` 0.85 — ぼかし半径
- `shadowOpacity` 0.34 — 濃さ
- `shadowColor` — 影の色（**黒ではなく、暗くなったリフレクタの色**）

> 影を黒にすると「印刷物」に見えます。反射面が暗くなっているだけなので、色はリフレクタ寄りにします。

### 4-5. 画面の外側の縁

ドット領域の外にも構造があります。**CSS の余白ではなく、シェーダで描いています。**

```
[ドット領域 160×144] → 露出したリフレクタ 約0.7ドット → 印刷マスク 約2.2ドット → モジュール端
```

理由は 2 つ。**リフレクタの粒が縁の下まで連続していないと嘘に見える**こと。**最外周のドットが落とす影が、その露出部に落ちる**必要があること。この 2 つで「素子とリフレクタの間に隙間がある」ことが読み取れます。

### 4-6. サブピクセル（GBC/GBA のみ）

カラー機はセルを R|G|B の縦 3 分割にします。**1 ストライプが 4 デバイス画素を切ると振幅を落として**、モアレを防ぎます（`SUB_CONTRAST = 0.55`、`smoothstep(2.0, 5.0, ...)` でフェード）。

## 5. PASS 3 — 残像

**1 画素ごとに「アナログな状態」を持ち、目標値へ指数的に近づけます。**フレームブレンドではありません。

```glsl
vec3 fall = step(target, state);              // 暗くなる方向か
vec3 tau  = mix(vec3(tauRise), vec3(tauFall), fall);
vec3 a    = 1.0 - exp(-dt / tau);
state     = mix(state, target, a);
```

### 5-1. 時定数は非対称

| 方向 | 物理 | 速さ |
|---|---|---|
| 暗くなる（`tauFall`） | 電圧で**駆動**される | **速い** |
| 明るくなる（`tauRise`） | 電圧を切って**自然に緩和** | **遅い** |

```
tauRise = (8 + 102 × ghost.strength) × tempMul
tauFall = tauRise × 0.35
```

DMG の `ghost.strength = 0.52` なので **tauRise ≈ 61ms、tauFall ≈ 21ms**。

> **ここは以前逆でした。**遅い側を「暗くなる」に当てており、キャラが移動先に現れるのが 1 フレームで 21% しか進まない一方、去った場所のほうが速く消えるという、実機と逆の絵になっていました。体感は「ボタンを押してワンクッションおいて自機が動く」で、**入力遅延と誤認しやすい**症状です（実際の入力系は実測 0.57 フレームで、遅延の主因ではありませんでした）。

> **未解決**: 同時代の STN モジュールは応答 100〜200ms とされます。brickboy の 61ms はその半分以下です。ただしこの文献値は汎用のキャラクタ表示用モジュールのもので、60fps のゲーム機向けに選ばれた DMG のパネルがそこまで遅いとは考えにくい。**実機の映像から尾の長さを測るまで、確かなことは言えません。**

### 5-2. 温度と暖機

```
tempMul = (1 + 2 × temperature) × warmupMul
```

`warmupMul` は起動から約 45 秒かけて 1.6 → 1.0 へ。**冷えている／点けたばかりのパネルは残像が長い**という性質です。

### 5-3. ゲート

`ghostGate`（DMG は 0.05）。目標との差が小さいときは即座に追従させます。これがないと、わずかな差が延々と残って画面全体がぼんやりします。

### 5-4. 実装上の注意

**dt は実時間（ms）**を使い、上限で刈ります。フレーム落ちしたときに一気に飛ばないようにするためです。

**オフライン描画（動画書き出しなど）では dt を固定**してください。brickboy は 1 フレーム = 16.742ms（= 70224 ÷ 4194304 秒）に固定しています。倍速で描いても、実時間で再生したときの残像量が実機どおりになります。

**履歴バッファは黒から始まります。**そのまま撮ると先頭が黒からのフェードインになるので、**最初のフレームを数十回捨て描き**して定常状態にしてから撮ります。この暖機を忘れると、測定の基準がずれます（§10-⑥）。

## 6. PASS 4 — 経年劣化と故障

**すべて既定 0**、つまり健康なパネルでは素通しです。適用順:

```
1. 全体の階調   dimming / frontlight / backlightBleed / contrastFade
2. 偏光板の劣化 screenRot（2 種類の模様）
3. 埃・しみ     dust
4. ライン抜け   deadLineSeverity（縦・横）
```

|---|---|
| ![健康](images/display/06-defect-pristine.jpg) | ![劣化](images/display/06-defect-vinegar.jpg) |

| ライン抜け 0.25 | 全体の暗み 0.4 |
|---|---|
| ![ライン抜け](images/display/06-defect-deadlines.jpg) | ![暗み](images/display/06-defect-dimming.jpg) |

### 6-2. ライン抜け

**これが最も作り込みが要る箇所です。** リボンケーブル／熱圧着の接触不良で、列（または行）の電極が浮く現象です。

| 要素 | 実装 |
|---|---|
| **どの列が抜けるか** | 列ごとのハッシュ（`seed` 依存）。時間では動かない |
| **端寄り** | `deadLineEdgeBias` 1.0 = 圧着部のある端に集まる |
| **帯になる** | 低周波ノイズで 2〜5 列の塊になる |
| **色** | リフレクタ色が主。一部は暗いまま（`deadLineLit` 0.06） |
| **長さ方向の濃淡** | 接触抵抗で端から端へ減衰（`gA`→`gB`、0.55〜1.0） |
| **明滅** | 約 5px の区間ごとに、接触が微妙な箇所だけランダムに明滅 |
| **にじんだ縁** | 隣の列とまたいで羽根付け（列の境目に継ぎ目を出さない） |
| **ドット越し** | 格子を通して描く。**棒ではなく点の連なり**になる |
| **横方向** | 行の抜けも出す（`deadLineRowRatio` 0.15 = 縦より稀） |

severity は**非線形**です（`sev^2.2`）。低い側を細かく使えるようにするためで、0.1 で約 1 列、0.25 で約 7 列、1.0 で約 92% が抜けます。

> **座標で名指しして塗る経路は持ちません。**以前は `deadColumns`（x, 幅, 濃さ）で個別指定できましたが、削除しました。理由は §10-② に書きます。

### 6-3. 偏光板の劣化

2 種類の模様を切り替えられます（`rotMode`）。

- **1（既定）**: 中心から侵食する放射状。いわゆる「ビネガーシンドローム」
- **0**: 不定形の斑（アメーバ状）

`fbm`（値ノイズの重ね合わせ）で有機的な輪郭を作り、`seed` で位置を固定します。**時間では変化しません。**

## 7. PRESENT — 仕上げ

最後に画面全体へ掛けます。

| パラメータ | 内容 | DMG の値 |
|---|---|---|
| `gradient` | 面内の明るさむら（低周波） | 0.08 |
| `grain` | マットな粒（固定ハッシュ） | 0.012 |
| `vignette` | 周辺減光 | 0.08 |
| `sheen` | 映り込み | **0（意図的に無効）** |
| `sheenHotspot` | 強い映り込みの芯 | **0（同上）** |

### 映り込みを描かない理由

**表示している液晶自体が、すでに環境を映しているからです。**

疑似的な映り込みを描くと、利用者のモニタが返す本物の映り込みと**二重になり**、かえって嘘くさくなります。実装は残してありますが、DMG プロファイルでは 0 にしてあります。

**再実装する方も、この判断を引き継ぐことをお勧めします。**（§10-① に経緯）

## 8. プロファイル全パラメータ

## 9. 表示以外で見た目に効くもの

### 9-1. 拡大方法

**Fill（既定）**: ゲームの画を画面の端から端まで伸ばし、**リフレクタの縁とベゼルは画面外へ逃がします**。実機の筐体が画面の外まで続いているのと同じ見え方になります。

**Integer**: 整数倍。にじみは出ませんが、段でしか伸びないので余白が出ます。

いずれの場合も、**バックバッファは実際のデバイス画素数ちょうど**に取ってください。ブラウザや OS に非整数倍の拡大をさせると、合成したドット格子が再標本化されて**モアレになります**。

### 9-2. 環境が見え方を変える（再現できない部分）

**同じ絵でも、見る環境で色の印象が変わります。**これは実装では再現できず、するべきでもありません。

| 経路 | 内容 |
|---|---|
| **Hunt 効果** | 色度が同じでも**輝度が上がると色みが増して見える**（CIECAM02 に組み込まれた標準的な色の見えモデル） |
| **表面反射との比率** | 強い直射光ほど無彩色の混入が減り、彩度が上がる |
| **光源スペクトル** | 蛍光灯の水銀輝線（405/436/**546**/578nm、546 は緑）と太陽光の連続スペクトルでは、同じフィルタを通しても出る色が違う |
| **濃度ダイヤル** | 明るい場所では上げがち → 暗く・緑寄りになる |

**4 経路すべてが「明るい地域ほど緑が濃く見える」方向に働きます。**「実機はもっと緑だった」という証言と、実機写真の個体差の大きさは、パネルの違いを持ち出さなくてもこれで説明がつきます。

## 10. 採用しなかったこと・撤回したこと

**この節がいちばん実用的かもしれません。** もっともらしい結論が何度も外れています。

### ① 映り込み（sheen）を描く → 却下

反射型液晶なので環境の映り込みが要る、と考えました。プロファイルの `sheen` が 0 だったのも「実装漏れ」に見えました。

**却下理由**: **表示しているモニタ自体がすでに環境を映しています。**疑似的な映り込みを足すと二重になり、かえって嘘くさくなります。`sheen: 0` は正しい設定でした。

### ② 座標で名指しして塗る「抜けた列／抜けた画素」→ 削除

`deadColumns`（x, 幅, 濃さ）と `deadPixels`（x, y, 状態）という、位置を直接指定する経路がありました。**削除しました。**

**理由**: どのプロファイルも使っておらず、UI からも触れず、型定義にも「`deadLineSeverity` が取って代わった」と書かれていました。そして**残っていると取り違えます**。実際に取り違えました —— 経年劣化をランダムに乗せる機能で「本数を厳密に決めたい」という理由からこちらを使い、作り込んだ見た目を全部捨てた絵を出しました。

**何が違ったか**:

| | `deadLineSeverity`（作り込んだ方） | 明示指定（削除した方） |
|---|---|---|
| 色 | 列ごとに漏れ量が違う | 一律リフレクタ色でベタ塗り |
| 端 | 隣の列とまたいで羽根付け | 境界で断ち切り。**硬い 1px 直線** |
| 長さ方向 | 接触抵抗で端から端へ減衰 | **上から下まで均一** |
| ゆらぎ | 区間ごとに接触不良が明滅 | **完全に静止** |
| ドット構造 | 格子を通した**点の連なり** | 格子を無視した**べったりした棒** |
| 太さ | 2〜5px の帯に固まる | **常にちょうど 1px** |
| 位置 | 端に寄る（実機の分布） | **等間隔**。1 本なら画面のど真ん中 |

**教訓**: 同じ現象に 2 つの経路を残さないこと。片方が「作り込んだ方」なら、もう片方は誤用の危険しかありません。

### ③ 起動ごとにランダムな経年劣化を乗せる → 撤去

「起動のたびに個体差を入れる」機能を作り、既定オンで公開しました。**撤去しました。**

**問題**: 上記②の経路を使ったため、作り込んだライン抜けとは似ても似つかない**硬い直線が画面中央に出ました**。しかも「Dead lines」のつまみは 0 のままなので、**画面に線が出ているのに設定からは追えません**でした。

**検証も機能していませんでした。**書いたテストは DOM の文字列（自分が乱数から作って書き込んだ値）を読んでおり、**画素を 1 つも見ていません**。7 項目すべて OK になりましたが、仕組みの差し替えは原理的に検出できません。

**教訓**: 画面に見えるものを変える機能は、**画素で検証する**こと。DOM の値や設定値を読むテストは検証と認めないこと。

### ④ 「実機の地の色は G/R = 2.6 の強い緑」→ 撤回

電源オンの実機写真 1 枚から、brickboy の地の色（G/R 0.86）は赤優勢で実機と逆だ、と結論しかけました。

**撤回理由**:

- その写真の EXIF は**彩度「強」・オートホワイトバランス**でした（EXIF を確認したのは指摘を受けた後）
- 比較に使ったもう 1 枚は **EXIF が完全に剥がされたブログ用の再エンコード画像**で、色の基準に使えるものではありませんでした
- **電源オフの実機 10 個体**で測り直すと、実測範囲 G/R 0.81〜1.89 に対し **2.6 は外れ値**でした

**教訓**: 写真から色を語るなら、**EXIF を最初に見ること**。ホワイトバランス・彩度設定・色空間を確認しないまま出した数値は根拠になりません。

### ⑤ 「色の向きが実機と逆」→ 計算の誤り

「実機は暗いほど緑が抜けるが brickboy は逆」と結論しました。**誤りです。**

`G−(R+B)/2` という指標を、**sRGB のガンマを外さずに**適用していました。線形に直すと**実機も brickboy も同じ方向**（暗いほど緑が強い）でした。

**教訓**: チャンネル比を語るなら**必ず線形光に戻すこと**。暗い写真ほどガンマで比が誇張されます。

### ⑥ 「明るい部分に格子が出ない」→ 解像度不足の見誤り

低解像度のブログ画像では、明るい背景に格子が見えませんでした。**高解像度の元ファイルでは、はっきり出ています。**つぶれていただけでした。

### ⑦ 「乱数の種が大きすぎてシェーダが壊れる」→ 実測で否定

シェーダに `int(uSeed * 1013.0)` があり、32bit int を超えると未定義。プロファイル既定の種は 3〜9 なのに、ある機能で最大 21 億を渡していました。

**否定理由**: 種を 3 から 21 億まで振って実測したところ、**基準との最大差 1.03、閾値超えの列は 0**。壊れていませんでした。

なおこの検証の最初の版では、**基準にした 1 枚目が「残像バッファが冷えた状態」**で、同じ種同士でも差 45 が出ていました。暖機を入れて差 0.00 になり、そこで初めて比較が成立しています。

### ⑧ 「余った領域をパネルの地の色で埋める」→ 却下

窓の形が合わずに帯が出る問題に対し、帯を地の色で塗って見えなくする案を出しました。

**却下理由**: パネルには濃いベゼルと角丸があるので**境目は見えたまま**です。**症状を塗り潰すだけで幾何は直っていません**。しかも画面が実際より広く見えるので、表示忠実性を売りにする道具としてはむしろ有害です。

## 11. 検証のやり方

見た目は主観になりやすいので、**測れるものは測ります。**

### 11-1. 付属の診断 ROM

`public/roms/check.gb`（`scripts/build-check-rom.mjs` で生成）。**実機でも動きます。**

| ページ | 見るもの |
|---|---|
| 1 TONE | 4 階調と 2×2 ディザ。色補正と暗部の潰れ |
| 2 GRID | 1px 縦線・横線・市松。ドット構造とモアレ、ライン抜け |
| 3 GHOST | 走る四角と静止した四角。**残像の量を並べて比べられる** |
| 4 INPUT | 押されているボタン。入力が届いているかの切り分け |
| 5 ALL ON | 全ドット点灯。**地の色が混ざらないので素子の色そのものが見える** |

**フラッシュカートで実機に表示して撮れば、同じ内容を並べられます。**写真から色を語るときの最大の弱点（被写体が違う）が消えます。

### 11-2. 現像ハーネス

`?renderfarm=1` で通常の UI の代わりにマウントされ、`window.__rf` から

```js
__rf.init(panelId, scale, defects)   // 故障の上書き付きで初期化
__rf.renderBatch(base64)             // 生フレームバッファ → 描画結果
```

が使えます。**表示パイプラインは PWA と同一物**なので、出力は画面表示と画素一致します。Node への移植や二重実装はしません。

### 11-3. 自動テスト

| スクリプト | 何を測るか |
|---|---|
| `test/render-defects.mjs` | 抜けた列の本数・輝度、無効値の扱い、再描画の一致 |
| `test/check-rom.mjs` | 診断 ROM が実際に動くか（8 項目） |
| `scripts/panel-color.py` | 写真から画面の色を測る（線形光・画像内の無彩色で正規化） |
| `scripts/make-display-figures.mjs` | この資料の図を生成 |

### 11-4. 測るときの落とし穴

- **残像バッファを暖機してから測る。**冷えたまま撮ると 1 枚目だけ暗く、基準がずれます
- **線形光に戻してから比を取る。**sRGB のまま比を出すと誇張されます
- **写真の EXIF を最初に確認する。**WB・彩度・色空間を見ずに数値を出さないこと
- **同梱 ROM に追随するテストを書かない。**ROM を差し替えると判定がぶれます。基準には差し替えない ROM を使うこと

## 12. 再実装チェックリスト

ゼロから作る場合、この順に確認してください。

**構造**

- [ ] 6 パスの順序（列集計 → 色 → 格子 → 残像 → 故障 → 仕上げ）
- [ ] 中間バッファは浮動小数点
- [ ] 残像は ping-pong する 2 枚
- [ ] バックバッファは実デバイス画素数ちょうど

**色（PASS 1）**

- [ ] DMG は 4 色 LUT、CGB/GBA は byuu/ares の変換
- [ ] 11 段階の適用順（§3-2）
- [ ] 濃度は階調3 を不動点とする mix
- [ ] クロストークは 1 次元（列）に潰してから適用

**構造（PASS 2）**

- [ ] 隙間はリフレクタ色。暗い線ではない
- [ ] 明るい階調ほど格子が薄い
- [ ] 落ち影の色は黒ではなくリフレクタ寄り
- [ ] ドット領域の外に露出リフレクタ＋印刷マスクを**描画で**作る
- [ ] カラー機のサブピクセルは、細かくなったら振幅を落とす

**残像（PASS 3）**

- [ ] **暗くなる方が速く、明るくなる方が遅い**（逆にしない）
- [ ] dt は実時間、上限で刈る。オフラインでは固定
- [ ] 差が小さいときのゲート
- [ ] 撮影前に暖機する

**故障（PASS 4）**

- [ ] 既定は全部 0（健康なパネル）
- [ ] ライン抜けは**手続き的に 1 経路だけ**。座標指定の経路を作らない
- [ ] 種は時間で変えない（位置は固定、明滅だけ時間で動かす）
- [ ] 故障は残像の**後**

**仕上げ（PRESENT）**

- [ ] 映り込みは描かない（表示装置がすでに映している）

**検証**

- [ ] 画素で測る。DOM の値や設定値を読むテストは検証と認めない
- [ ] 写真を使うなら EXIF を先に見る
- [ ] チャンネル比は線形光で
